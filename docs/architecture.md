# Model and system boundaries

Sense → predict → detect → decide → act → verify → replan. Synthetic events update a persistent batch. Tool-based investigation reads batch state, freshness, buyers/routes, ranks options, checks policy and proposes an action. Human approval revalidates policy and commits a destination change atomically with its trace. Optimistic version checks reject stale investigations and approvals. Subsequent events trigger another investigation. Physical actuation remains a simulated adapter.

The live Responses API loop lets the model select tool order and inspect exceptions, bounded to 10 responses and 16 calls. Tool prerequisites and policy are deterministic. The model cannot call approval, invent authoritative prices, override a safety hold or change buyer constraints. Credentials and model name must be explicitly configured. Mock-provider tests validate protocol plumbing, not actual model competence. Tool results follow the [official function-calling workflow](https://developers.openai.com/api/docs/guides/function-calling).

## Simulation

M0 uses arrival order, static buyer assignments (50% retailer, 30% wholesale, 20% processor by batch-ID bucket), and morning prices for planning. M1 retains those contracts but uses estimated-RSL FEFO. M2 uses OR-Tools CP-SAT to jointly allocate whole lots for each day with fixed FEFO loading slots. Binary lot/buyer choices maximize forecast net proceeds, subject to one destination per lot, payload, daily buyer demand, fleet mass budget, conservative arrival freshness, receiving windows and grade requirements. Values are integer paise and kilograms. One solver worker, fixed seed and deterministic search budget make runs repeatable. OPTIMAL/FEASIBLE or explicitly labeled fallback status is retained; a feasible solution is not claimed globally optimal.

M3 starts with the identical M2 plan, then observes events at the shared junction, checks alternatives, accounts for approval delay and performs bounded interventions. Each model experiences identical latent batches and exogenous market/physical events. M0/M1/M2 cannot see future events or latent physical RSL at planning time. Morning buyer availability and demand are observable; later cancellations, spot prices and disruptions are revealed only at event time. Actual acceptance uses realized condition, grade, active buyer and arrival window, independently of the predicted value. A successful reroute is not an automatic sale. The synthetic graph has a six-hour depot-to-junction trunk and destination branches, so diversions originate at the actual modeled junction. No overnight carryover or full multi-stop fleet routing is modeled.

Daily buyer reservations cannot exceed capacity; fleet dispatch mass is bounded and each lot is below vehicle payload. M3 releases a superseded reservation before reallocation and retains original transport as a sunk cost. Transport costs for diversion are added, not substituted. Unallocated, rejected and safety-held lots are conservatively written off. Thus the reported spoilage measure includes commercial unsold inventory. Safety violations count dispatch outcomes violating known holds; zero is an enforced invariant, not evidence of real-world safety.

The quality proxy is `remaining = max(0, initial - duration × 2^((temperature−20)/10))`. Initial latent RSL is adjusted by explicitly synthetic maturity/grade factors; sensor-estimated initial RSL includes Gaussian error. Temperature histories contain separate physical and observed values. Queue aging, remaining travel at reference temperature and approval delay are subtracted. Conservative estimated RSL subtracts max(6 hours, twice the scenario prediction-error standard deviation). This is an engineering buffer, not a calibrated confidence interval. [UC Davis Tomato Produce Facts](https://postharvest.ucdavis.edu/produce-facts-sheets/tomato) supports temperature/maturity dependence; it does not validate these coefficients. Humidity histories are recorded but have no invented quantitative deterioration coefficient. Cultivar, chilling injury and pathogens are not modeled. Calibration targets only the aggregate CASE baseline; it does not validate the biological model.

## Financial definitions

- Gross revenue = accepted kg × channel price. Rejected/write-off lots produce zero revenue.
- Operating profit = revenue − procurement − transport − handling − rescue − technology operations. Procurement applies to all input kg. Write-offs and markdowns are not subtracted again.
- Net realization per input kg = (revenue − all operating costs except procurement) / input kg.
- **Net batch realization margin** is operationally defined as operating profit / gross revenue, equal to operating profit margin. This interpretation needs confirmation against the original case wording. It is undefined when revenue is zero.
- Relative margin uplift = Mx margin / M0 margin − 1, defined only for positive baseline margin. Percentage-point change = 100 × (Mx margin − M0 margin).
- Incremental profit is Mx−M0. Incremental event-driven policy profit is M3−M2. Do not attribute M1/M2 improvements to the agent.
- M3 period ROI = (incremental operating profit vs M0 − setup cost) / setup cost. Payback days = setup cost / average daily incremental profit. Null when economically undefined. Extrapolated payback assumes the period repeats; it is not a forecast.
- Buyer rejection denominator: attempted non-held deliveries. On-time fulfilment denominator: all input batches, deadline 24 hours including queue and shared trunk. Buyer receiving window is 30 hours. Rescue success denominator: all M3 intervention attempts, success requires acceptance at a changed destination.
- Target success: spoilage below 10% AND relative margin uplift at least 12%. Probability is an empirical frequency across seeded repetitions, not a population estimate or statistical assurance.

All prices/costs and operating conditions remain illustrative. Baseline calibration and independent evaluation are documented in `research/calibration_log.md`. The boundary calibration solution and all unfavorable evaluation outcomes must remain visible.

## Ledger and replay

Every outcome has one signed sales entry and exactly one entry per cost category. Processor salvage is a revenue subset, not an additional receipt. Financial waterfall entries sum to operating profit. Frozen experiment results are immutable. Run-scoped interactive replay reserves daily buyer capacity under a database row lock, revalidates approval and records persistent action outcomes. Its decisions do not rewrite the historical simulation results; this boundary is returned in the API. Batch-level audit currently exposes repetition 0; all repetition-level KPIs and distributions remain available.
